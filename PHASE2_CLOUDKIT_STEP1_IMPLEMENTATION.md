## CUSTOM ZONE

Two zones, per the approved plan — modelled in code, **not created remotely**:

| Zone name | Record types |
|---|---|
| `PersonalAICore` | `Memory`, `Rule`, `StyleProfile` |
| `PersonalAIChat` | `Conversation`, `Message` |

`CloudKitZoneManager` creates them lazily (`ensureZones()` before the first
write) and deletes both for `deleteAllData`. The per-zone `CKServerChangeToken`
is the sync cursor, encoded (with both zones' tokens) into the opaque
`SyncPullResult.cursor` string via `CloudKitSyncCursor`.

## RECORD TYPES

5 types. One `CKRecord` per canonical entity, keyed by the canonical UUID.
Fields (identical on every type):

| Field | Encrypted | Purpose |
|---|---|---|
| `payload` | **yes** (`encryptedValues`) | the entity's full canonical JSON (`PersonalSyncCodec` output) |
| `deletedAt` | **yes** | soft tombstone, mirrors payload |
| `recordKind` | no | `PersonalRecordKind.rawValue` — type-confusion guard |
| `clientUpdatedAt` | no | the entity's `updatedAt` / `timestamp` |
| `schemaVersion` | no | `PersonalMemoryDocument.currentSchemaVersion` |

`Revision` is **not** a v1 CloudKit type — revision history stays local and in
local backup/export, matching the current architecture. A corrupt `payload`
can damage exactly one entity.

## STABLE ID STRATEGY

`CKRecord.ID(recordName: <canonical UUID>.uuidString, zoneID: <core|chat>)`
for every type (`CloudKitRecordID.make`). The adapter always constructs the
id; **CloudKit never mints an identity the app depends on**. `remoteID` is set
to a zone-qualified debug hint only; nothing keys off it. Verified by
`CloudKitRecordIDTests` (7 tests: determinism, verbatim UUID, round-trip, zone
placement, collision-free, cross-kind guard, style-profile singleton id).

## PORTABLE USER IDENTITY

Canonical identity stays **`PersonalAIUserID`** — the EvenAI account id already
flowing through `ownerBox.ownerID`. **`RootView.swift` is NOT changed.**

The CloudKit adapter holds a private `CloudKitAccountBinding
{ personalAIUserID, ckUserRecordName, boundAt }` in its local state store. The
iCloud user record name is **infrastructure identity only** — never written to
a record, a bundle, or an export. A future Postgres adapter creates its own
binding; no record, bundle, or `SyncableStyleProfile.stableID` value changes.

## ACCOUNT SWITCH SAFETY

`CloudKitAccountEvaluator.evaluate(status:currentICloudUserRecordName:binding:
personalAIUserID:)` — a pure, total, deterministic decision function →
`CloudKitAccountState`:

| State | Sync | Behaviour |
|---|---|---|
| `.noAccount` / `.restricted` | frozen | keep all local data |
| `.indeterminate` | frozen | retry later |
| `.unbound` | allowed | bind to the current account on first use |
| `.bound` | **allowed** | normal sync |
| `.reconciliationRequired(reason)` | **frozen** | **no auto-upload, no auto-merge, no auto-delete, no silent rebind**; observable via `service.currentAccountState()` for the UI |

The A → signed-out → B flow: the mismatch is detected before any push/pull;
`push`/`pull`/`snapshot` throw `PersonalCloudTransportError.unauthorized`,
which the **unchanged** engine turns into `.failedRetryable` (all pending
changes stay queued, cursor untouched, local data intact). Switching back to A
matches the binding and resumes. Verified by `CloudKitAccountSwitchTests` (7
tests) — including "A's data is never uploaded into B's database"
(per-iCloud-account partitions in the double), "B never becomes the canonical
owner", "cache intact throughout", and "reconciliation state is observable
without a sync attempt".

## CKSYNCENGINE IMPLEMENTATION

**`CKSyncEngine` is NOT used**, per the approved plan. The adapter is
`CKModifyRecordsOperation` + `CKFetchRecordZoneChangesOperation` +
`CKModifyRecordZonesOperation` behind `CloudKitDatabaseFacade`, driven by the
existing `PersonalAISyncEngine` (unchanged).

- **Cursor:** two per-zone `CKServerChangeToken`s, base64-JSON-encoded into the
  opaque `SyncPullResult.cursor`. Garbage / stale / partial → safe per-zone
  full re-fetch.
- **`Int` `baseRevision` ↔ CloudKit change tag:** bridged by a persisted local
  side-table (`CloudKitAdapterState.records`) that assigns a monotonic
  `syntheticRevision` per record and stores the change tag. **No change to any
  Core type.**
- **Conflicts:** a stale-tag save returns `.conflict(serverRecord, …)` → the
  adapter builds a `SyncConflict` → the existing `PersonalConflictResolver`
  per `ConflictPolicy`. Verified deterministic.
- **Idempotency:** id-keyed upserts + a token-expiry full re-fetch never
  duplicate (tested).
- **Errors:** `CloudKitErrorMapper` classifies every `CKError` into
  `retryable` / `requiresAccountAction` / `requiresReconciliation` /
  `fatalForOperationOnly`, and maps to a `PersonalCloudTransportError` for the
  seam. **No classification clears local data** — the engine's only failure
  outcome is `.failedRetryable`.

## RESTORE FLOW

`snapshot(ownerID:)` fetches both zones from `nil` tokens (paged, bounded),
assembles a `PersonalDataBundle` via the existing `PersonalBundleAssembler`,
and persists the ending token pair so the first incremental pull after a
restore continues cleanly (robust to the restore coordinator passing a cursor
computed for a different backend shape). `PersonalAICloudRestoreCoordinator`
and `PersonalBundleAssembler` are **unchanged**.

`PersonalDataImporter.replaceAll` gained an 11-line fix (see RELIABILITY
HARDENING #2): it now **preserves the device's local `PersonalSyncState`**
instead of taking the bundle's.

Verified by `CloudKitRestoreTests` (8 tests): full restore, stable-id
preservation, idempotent repeat restore, tombstones respected, incremental
continuation after restore, interrupted/resumable restore with a 3-record
page size (25 records), 200-message pagination without whole-conversation
rewrite, and "a failed restore leaves prior local records untouched".

## RELIABILITY HARDENING (this pass)

### 1 — Adapter state is now persisted

`CloudKitAdapterState` holds: the **`PersonalAIUserID ↔ iCloud account`
binding**, the **two per-zone `CKServerChangeToken`s** (sync/restore cursor),
and **per-record change tags + synthetic revisions**. All of it must survive
an app relaunch — losing the binding on relaunch would defeat A→B protection
(a device relaunched on account B with no binding would silently bind to B).

- `FileCloudKitAdapterStateStore` — sealed through `DocumentFileStoring`
  (`EncryptedDocumentFile` in production, `PlaintextDocumentFile` in tests);
  writes are **atomic** (`Data.write(options: [.atomic, .completeFileProtection])`).
- `CloudKitPersonalCloudService.makePersisted(database:stateDirectory:
  documentFile:personalAIUserID:)` — the composition a real `.connected`
  wiring will use. **`PersonalAIContainer.live` is not changed** — it still
  wires `cloudService: nil` / `.notConfigured`, and the bare adapter `init`
  still defaults to an in-memory store for explicit test control.
- `CloudKitAdapterState.adapterStateVersion` (currently `1`) — a file from a
  newer adapter is treated as unreadable → safe reset.
- **Corruption is always safe for canonical data:** a missing / unreadable /
  corrupt / too-new state file yields `.empty` (a clean re-bootstrap — the
  adapter re-fetches from a `nil` token and re-binds to the current iCloud
  account). Nothing in this path can reach the Personal AI memory store.
- **`reconciliation-required` is derived, not stored** — it is recomputed by
  `CloudKitAccountEvaluator` from `status + currentUserRecordName + binding`.
  Persisting the *binding* is what makes A→B protection survive relaunch; the
  reconciliation verdict follows automatically.
- **No secrets serialized** — only opaque server strings, ints, dates, and
  two identifiers (`personalAIUserID`, the iCloud user record name). A test
  greps the on-disk bytes for token/secret patterns and asserts the JSON has
  only the five expected keys.

Verified by `CloudKitAdapterStatePersistenceTests` (9 tests): binding
survives relaunch · A→B protection survives relaunch (persisted binding + new
account → `.reconciliationRequired`, nothing uploaded to B) · cursor + tags
survive relaunch · corrupt file → `.empty` no throw · too-new version →
`.empty` · deleted file → clean re-bootstrap · corrupting the file mid-life
never touches the memory store · no secrets serialized · encrypted-file
round trip.

### 2 — Restore no longer mutates the local sync preference

**Investigation:** `.replaceAll` restore replaced the whole
`PersonalMemoryDocument`, including its nested `PersonalSyncState`, so a
cloud restore silently set `cloudSyncEnabled` (and `cursor`,
`syncedRevisions`, backup history) to the bundle's values. The restore
coordinator was already compensating for the wiped `cursor` /
`needsCloudRestore` — but not `cloudSyncEnabled`.

**Determination:** `PersonalSyncState` is **local runtime/config state (B)**,
not canonical user data. Its own doc comment says so ("Local bookkeeping …
never uploaded verbatim"), and a backup's `cursor` / `syncedRevisions` are
meaningless on another device. There is **no deliberate Phase 2 contract**
that a restore should reset it — no test asserted the old behaviour.

**Smallest safe fix (11 lines, `PersonalDataImporter.replaceAll`):** capture
`memoryStore.loadSyncState()` before the swap and re-apply it to the incoming
document, so the device's own sync state is preserved. `.merge` never touched
`syncState` and is unchanged.

**Invariant now holds:** `cloudSyncEnabled` (and the whole local
`PersonalSyncState`) is identical before and after a successful `.replaceAll`
restore. Fresh install uses `PersonalSyncState.empty` (the documented
default), never an accidental bundle value.

Verified by `PersonalDataRestorePreferenceTests` (6 tests): preserves
`true` · preserves `false` · preserves the full bookkeeping (cursor,
`syncedRevisions`, backup version) · failed restore preserves preference +
data · repeated restore preserves preference · fresh-install uses the
documented default not a bundle value.

## KNOWN LIMITATIONS

1. **No real CloudKit.** `LiveCloudKitDatabaseFacade` is compiled but never
   run — no container, no entitlement, no account. Its `CKOperation` block
   names and result-block shapes are from stable APIs but are **unverified
   against a live database**. First real exercise is the
   Development-environment integration suite + STEP 9 physical-device test.
2. **`PhysicalDeviceVerified = NO.**` `CKSyncEngine`-style edge cases (account
   switch mid-operation, large first push, `changeTokenExpired` in the wild,
   silent-push wake-ups) can only be confirmed on hardware.
3. **~~`.replaceAll` restore resets `cloudSyncEnabled`.~~ RESOLVED** —
   `PersonalDataImporter.replaceAll` now preserves the device's local
   `PersonalSyncState`. See RELIABILITY HARDENING #2 +
   `PersonalDataRestorePreferenceTests`.
4. **~~Adapter side-table is in-memory in tests.~~ RESOLVED** —
   `FileCloudKitAdapterStateStore` (sealed, atomic) + the
   `makePersisted(...)` composition are in place and tested for relaunch
   survival, corruption safety, and "no secrets serialized". It is not yet
   *wired into `PersonalAIContainer`* — that happens at
   real-CloudKit-configuration time — but the real adapter no longer depends
   only on in-memory state.
5. **Not wired into `PersonalAIContainer.live`.** Production is still
   `.notConfigured` by design. The `.connected` branch (behind a flag, then
   default only after STEP 9) is a later step.
6. **Revision history is local-only** (v1 design) — a second device builds its
   own history from the synced current state.
7. **Server-side headless read of private CloudKit memory remains the open
   Phase-3 risk** (unchanged; `PHASE2_CLOUDKIT_STEP1_PLAN.md`).
8. **CKRecord record names are bare UUIDs**; cross-kind collision is
   effectively impossible (independent `UUID()` generation) and additionally
   guarded by the `recordKind` field, but not structurally prevented by a
   prefix (kept verbatim per the approved plan and for Postgres-PK reuse).
