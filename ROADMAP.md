# Even AI — Roadmap

Milestones are implemented and verified strictly one at a time. Each requires explicit approval before the next begins.

**Current version: `0.2.0`** — Milestone 2, frozen 2026-07-28. Tagged `v0.2.0` in both repos.

## ✅ Milestone 1 — Conversations Feature (Mock)
- SwiftUI skeleton: `App/Core/Infrastructure/Features` architecture, XcodeGen-managed project.
- Chat list: create, rename, delete, auto-title from first message.
- Chat screen: ChatGPT-style bubbles, timestamps, multiline input, typing indicator, smooth auto-scroll.
- SwiftData persistence (`ChatEntity`/`MessageEntity`), restored automatically after relaunch.
- `MockChatService` with simulated word-by-word streaming replies.

## ✅ Milestone 2 — Production Backend Integration (frozen)
- Backend: new additive `src/chat/` module on `even-ai-assistant-asr` — REST endpoints for conversations + SSE streaming endpoint, real OpenAI integration, JSON-file persistence. `/session` (ASR) verified byte-for-byte unchanged.
- iOS: `NetworkChatService` (REST + SSE, retry-with-backoff, actor-isolated) replaces `MockChatService` as the live implementation; `AppContainer` is the only file that changed to make the swap, per the original design intent.
- End-to-end verification pass: found and fixed a startup crash (env-var load order), an information-disclosure bug (raw stack trace on malformed JSON), a Swift 6 concurrency violation, a Sendable warning, and three distinct silent-failure paths in message sending.
- Full production readiness review (whole-codebase, not just the diff): found and fixed a second backend crash risk (SSE heartbeat writing after client disconnect), two iOS error-handling correctness bugs (a failed delete corrupting local state, a missing reentrancy guard on chat creation), a retry-idempotency gap (create was being retried), and two stale doc comments. Two further findings were reviewed and explicitly deferred as documented, non-blocking limitations (see below) rather than fixed, to avoid scope creep into new feature work.
- All fixes covered by automated tests where the underlying logic is unit-testable (view-model layer); confirmed via live curl-based end-to-end testing for everything backend-observable, including a deliberately-timed mid-generation client disconnect.
- **Final freeze pass**: full re-verification (all 10 end-to-end backend checks re-run live, including a repeat of the mid-stream-disconnect crash regression check) and a project-wide cleanup scan (TODO/FIXME comments, dead code, duplicate files, unused imports) — nothing further found to fix or remove; both repos build clean with zero warnings. Tagged `v0.2.0`.

## 🚧 Milestone 3 — Authentication (in progress)

Full design approved 2026-07-28 — anonymous-by-default accounts (never a forced gate), claimed in place on sign-up (zero data migration), explicit merge-on-sign-in for a second device's local chats, ecosystem-wide from day one (platform-agnostic REST/JWT design, ready for Android/Web/Voice/Vision/Glasses without another auth rewrite). Implemented one small phase at a time, verified before each next phase begins.

- ✅ **Phase 3.1 — Backend: accounts, sessions, tokens (data model only, no endpoints yet)**. `src/auth/{db,store,tokens}.js`. Accounts (with subscription/settings/profile fields ready for future use), devices (platform-agnostic, one row per device per login), sessions (refresh tokens, hashed, revocable individually or all-at-once for "logout everywhere"). SQLite (`better-sqlite3`) chosen over the chat store's JSON-file pattern — see `ARCHITECTURE.md`. 17 new unit tests (Node's built-in test runner, zero new test-framework dependency), all passing. `/session` and existing chat endpoints re-verified live, unaffected; no new HTTP routes exposed yet.
- ✅ **Phase 3.2 — Backend: auth endpoints**. `POST /api/auth/{device,signup,login,refresh,logout,logout-all}`, plus `src/auth/middleware.js` (`requireAuth`). Refresh tokens rotate on every use; logging in twice from the same device retires that device's previous session (no unbounded session pileup); email enumeration avoided (same error for "no such account" and "wrong password"); account responses never include the password hash. `/api/auth/merge` deliberately **not** built yet — it reassigns a device's chats to a newly-signed-into account, but chats have no `account_id` until Phase 3.3, so building it now would mean a placeholder with nothing to do; `login`'s response already includes `mergeAvailableFrom` so the client can detect the situation today. 18 new endpoint-level tests (`supertest`, testing the router in isolation from `server.js`'s OpenAI/PORT/exit side effects), all passing — 35/35 total across the auth module. `/session` and existing chat endpoints re-verified live, unaffected.
- ✅ **Phase 3.3 — Backend: scope chat by account, `/api/auth/merge`**. Every `/api/chats*` and `/api/chat/stream` route now requires `requireAuth` and is scoped to `req.accountId`; a chat belonging to a different account 404s identically to a chat that doesn't exist (never a distinguishing 403 — avoids confirming existence to someone who shouldn't know). `requireAuth` now checks per-request that the access token's underlying session hasn't been revoked (access tokens carry a `sid` claim as of this phase) — without this, `logout`/`logout-all` would only block *future* refreshes, leaving any already-issued access token valid for its full 30-minute life; verified live and in tests that chat access is cut off immediately after logout, not just eventually. `POST /api/auth/merge` built (idempotent by construction — reassignment, not copying, so a second call moves zero chats), restricted to merging only *unclaimed* (anonymous) accounts, closing what would otherwise be an account-takeover vector. One real bug found via live verification and fixed: chat responses were leaking the internal `accountId` field; trimmed via a `toPublicChat` mapper, same principle as auth's `toPublicAccount`. 21 new tests (ownership violations, expired/revoked-session rejection, merge + duplicate-merge protection) — 55/55 passing across the whole backend. Pre-Phase-3.3 chats (created before any account concept existed) are now permanently unreachable — treated as orphaned dev data rather than an invented migration, since no real users exist against this backend yet. `/session` re-verified unaffected throughout.
- ✅ **Phase 3.4 — iOS: auth foundation**. `Core/Domain/{User,AuthResult,AuthError,AuthServicing}.swift`; `Infrastructure/Security/AuthTokenStore.swift` (refresh token only, Keychain, `.afterFirstUnlockThisDeviceOnly` — opts out of iCloud Keychain sync since a session must stay bound to its device); `Infrastructure/Networking/AuthenticatedAPIClient.swift` (new subfolder — the one shared, actor-isolated client every authenticated service is meant to reuse, owning the in-memory access token, single-flight refresh-on-401, and offline/http/session-expiry error classification); `Infrastructure/Auth/{NetworkAuthService,MockAuthService,AuthAPIDTOs}.swift`; `App/AuthState.swift` (app-wide observable auth state + actions, injected via `.environment()` alongside `AppState`, not a singleton). `AppContainer` now constructs one `AuthenticatedAPIClient` and injects the same instance into `authService`; `chatService` is deliberately *not* wired to it yet (Phase 3.5). `RootView` triggers `authState.restoreSession()` on launch without gating or blocking the UI on it. 30 new tests (login/logout/restore/refresh/single-flight/offline/revoked-session/Keychain round-trip/DI), all passing (manually traced against the implementation given this environment's Simulator limitation — see Phase 3.4's report). No chat wiring, no UI, no login screens — exactly this phase's scope. `NetworkChatService` still makes unauthenticated calls and will continue 401ing until Phase 3.5.
- ✅ **Phase 3.5 — iOS: wire chat to auth**. `NetworkChatService` rewritten to route every call through `AuthenticatedAPIClient` — zero direct `URLSession`/`URLRequest` use left in chat networking; the SSE line-parser (event:/data: framing) is unchanged, only *how* the byte stream is obtained changed. `AppContainer.chatService` now shares the same `apiClient` instance as `authService`. **Architecture change**: `AuthenticatedAPIClient`'s recovery went from "refresh or fail" to two-tiered — a failed/missing/revoked refresh token now falls back to re-authenticating as the device's anonymous session automatically (`recoverSession()`, replacing Phase 3.4's `restoreAccessToken()`/`ensureRefreshed()`), so a chat request that outlives its session keeps working transparently (against the now-anonymous account) instead of throwing a dead end — this is what makes "if refresh fails, cleanly transition to the signed-out state" and "continue chatting" simultaneously true. Also ported Milestone 2's transient-failure retry (idempotent methods only, POST not retried by default) from `NetworkChatService` into the client, so no service needs its own retry logic either. `NetworkChatServiceError` reduced to just the one genuinely chat-specific case (`.server`, an SSE-level business error) — transport failures now propagate as `AuthenticatedAPIClientError` directly. **Zero changes** to `Features/` (every ViewModel/View) or `Infrastructure/Persistence` — confirmed via `git diff --stat`, not just by intent. 15 new tests (authenticated chat, automatic refresh-and-retry invisible to the caller, revoked-session→anonymous-fallback→chat-still-works, restored-session, SSE parsing unchanged through the new transport, business-level stream errors) plus 4 rewritten Phase 3.4 tests for the renamed/expanded recovery behavior — 49 iOS auth/chat-networking tests total. Backend re-run clean (55/55, untouched this phase); live end-to-end curl confirmed the exact request/response shapes the new Swift code relies on, including that a refresh correctly invalidates the prior access token (Phase 3.3's per-request session-revocation check).
- ✅ **Stabilization Sprint (2026-07-29)** — full release audit performed across both repos, then every Critical/High finding fixed before continuing to Phase 3.6. Backend: `server.js`'s catch-all error handler (extracted to `src/errorHandler.js`) now always returns a generic JSON 500 instead of falling through to Express's default stack-trace page; `express-rate-limit` added to `/api/auth/{login,device,signup}`; `login`'s not-found-account branch now runs a dummy `scrypt` hash so it no longer returns measurably faster than the wrong-password branch (closing the timing side-channel that undermined its own anti-enumeration design). iOS: `AuthenticatedAPIClient`'s 401-recovery guard no longer requires an access token to already be present (`recoverOn401` parameter, defaulting `true`; `login` opts out explicitly, since its 401 always means wrong credentials) — fixes a cold-launch race where the chat list could show a false "Can't Connect" error if its first fetch lost the race against launch-time session restoration; `project.yml` now defines `EVEN_AI_API_BASE_URL` per build configuration instead of one value for every build, so Release no longer silently points at `localhost` (Release currently holds a deliberately-invalid placeholder pending the real Railway URL). Backend: 59/59 tests passing (4 new). iOS: build-for-testing clean, zero warnings (2 new tests). No architecture changed beyond what each fix required; no new functionality added.
- ✅ **Phase 3.6 — iOS: Auth UI**. New `Features/Auth/Presentation/` module: `AuthWelcomeView` (entry point, presented as a sheet — never automatic, since every device already has a working anonymous account), `LoginView`/`LoginViewModel`, `SignUpView`/`SignUpViewModel`, `ForgotPasswordView` (backend has no password-reset endpoint, so this states that plainly instead of a dead link or a fake form). Settings gained an Account section: loading state while `authState.isRestoringSession`, signed-in identity + Sign Out/Sign Out Everywhere (behind one confirmation dialog) when claimed, "Sign In or Create Account" when anonymous. Two new `Core/DesignSystem` components (`FormTextField`, `InlineErrorText`); `PrimaryButton` gained an additive `isLoading` parameter (default `false`, every existing call site unaffected) so async actions don't jump the layout while pending. **Design decision**: `LoginView`/`SignUpView` take an explicit `onAuthenticated: () -> Void` closure rather than `@Environment(\.dismiss)` — they're reached by pushing onto `AuthWelcomeView`'s own `NavigationStack`, where `dismiss()` only pops one screen; closing the whole sheet on success needs the presenter's (`SettingsView`'s) own dismiss, threaded down explicitly. Both view models hold `AuthState`, never `AuthServicing` directly, matching `AuthState`'s own stated contract as the single place `currentUser` gets updated. All error messages route through `AuthError.errorDescription`, which was already written to never leak a raw backend message. No gating anywhere: chat remains fully usable anonymously; the auth UI is opt-in only, reached from Settings. 9 new unit tests (`LoginViewModelTests`, `SignUpViewModelTests`, validation/submission/error-mapping, using the existing `MockAuthService`/`FailingAuthService` doubles) plus 1 new XCUITest (`testAuthWelcomeNavigation`, full Settings → Welcome → Login/SignUp/Forgot-Password → Cancel smoke test) alongside the pre-existing `testLaunch`/new `testSettingsShowsAccountSection`. Fixed one real bug found while writing the UI tests: `.accessibilityIdentifier` applied to `FormTextField`'s outer container never reached the actual `TextField`/`SecureField` XCUITest queries against, since the container isn't a merged accessibility element — added an explicit `identifier:` parameter applied directly to the control instead. `xcodebuild build-for-testing` clean, zero warnings (also fixed a latent Swift 6 concurrency warning on the pre-existing `testLaunch`, unrelated to this phase's own code, by marking the UI test class `@MainActor`). Backend re-confirmed 59/59, untouched. Live curl re-verified signup/login/wrong-password against the real backend match exactly what `NetworkAuthService`'s DTOs expect.

## Known gaps carried forward (tracked, not blocking)

- No local offline cache for the production (`NetworkChatService`) path — the app is fully backend-dependent today. SwiftData persistence exists but is currently only exercised by `MockChatService`.
- No retry on a broken SSE stream, or on chat creation (both non-idempotent risks — see `ARCHITECTURE.md`); failures are surfaced as `.failed` messages instead.
- Backend persistence is a JSON file, not a database — fine for current scale; also has no per-chat write locking (unreachable today, see `ARCHITECTURE.md`'s production-readiness-review section), worth revisiting together before real multi-user/multi-device load.
- No tap-to-retry on a failed message, and auto-scroll doesn't pause when the user has manually scrolled away from the bottom during streaming — both minor UX gaps, not correctness bugs.
- No AppIcon artwork yet.
- **Live Simulator verification has not been possible in this development environment** across two separate review sessions (confirmed environmental — a fresh device shows the same instability). All fixes in both milestones are verified via clean builds under Swift 6 strict concurrency, live backend testing via curl (including real OpenAI streaming and a deliberately mid-stream client disconnect), and automated unit tests where the logic is testable outside the Simulator. A real on-device/Simulator run — visual streaming smoothness, actual memory profiling via Instruments, UI responsiveness under load — is still outstanding and should be the first thing done on a working Simulator setup before Milestone 3.
