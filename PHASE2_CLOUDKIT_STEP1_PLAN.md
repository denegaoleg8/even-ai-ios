**Status:** discovery only. Nothing in this document has been executed.
No production code changed, no Xcode capability altered, no CloudKit schema
created or deployed, no external account touched, no commit, no push.

**Scope:** map the committed Phase 1/2 Personal AI architecture onto a real
Apple CloudKit private database, and produce an exact, reviewable plan for
implementing the `CloudKitPersonalCloudService` adapter — **without building
it yet**.

**Revision (this pass):** an architecture review of the two highest-risk
decisions — storage granularity and user identity — was requested before
approval. Outcomes are folded in below and summarised in
**ARCHITECTURE REVIEW OUTCOMES**. Headline: the schema is
**record-per-canonical-entity** (it was already, but is now unambiguous and

Personal AI user identity stays **app-level and provider-independent** —
CloudKit's user identifier is treated as infrastructure identity only.

PRIMARY = CloudKit private database · LOCAL = encrypted iPhone cache
(already built) · INDEPENDENT BACKUP = Cloudflare R2 (later) · OPTIONAL
SERVER/API = Cloudflare Workers (later).

## PRIVATE DATABASE DESIGN

- **Database:** `container.privateCloudDatabase` only.
- **Access identity:** the device's signed-in iCloud account (system-managed;
  the app never handles a password or token). `CKContainer.accountStatus()`
  gates every operation.
- **Isolation:** structural — a private database has no query surface that
  can return another user's records. Nothing to configure, nothing to get
  wrong (unlike RLS / security rules).
- **Canonical user identity:** `PersonalAIUserID` — an **app-level,
  provider-independent** string. See PORTABLE USER ID DESIGN. CloudKit's own
  user identifier is used **only** by the adapter, to bind and to detect
  account switches — it never becomes the value stored in records or
  bundles.

## PORTABLE USER ID DESIGN

### CURRENT OWNER ID DESIGN (Phase 1/2, as built)

- Every syncable record carries `ownerID: String?` (`nil` = the local,
  pre-auth user).
- `PersonalAIService.updateOwner(_:)` is called from `RootView.swift` with
  `authState.currentUser?.id.uuidString` — **the EvenAI account UUID**
  (from `User.id`, a `UUID`). Per `User.swift`, every device gets an EvenAI
  account automatically and it keeps the **same id before and after signup**
  — i.e. it is already a stable, app-level identity, not a backend-session
  artefact.
- `ownerID` is consumed by: server-side record filing (future),
  `SyncableStyleProfile.stableID(ownerID:)` (deterministic singleton id),
  future R2 backup key-scoping, and multi-account-on-one-device safety.
- It travels inside `PersonalDataBundle` records (export / backup /
  snapshot).

### PROPOSED CLOUDKIT CHANGE — **REJECTED**

The earlier draft proposed feeding `ownerID` from
`CKContainer.userRecordID().recordName`. **Reverted.** Reasons:

- It couples the *canonical, portable* Personal AI identity to a
  **CloudKit-specific** identifier. A later migration to Postgres /
  Supabase / another provider, or a second client platform, would then need
  an identity remap across every record and every exported bundle.
- The CloudKit user record name is not meaningful outside CloudKit and not
  something the user can carry.
- `SyncableStyleProfile.stableID(ownerID:)` would change value on a provider
  swap, creating a duplicate style record.

### RECOMMENDED PORTABLE DESIGN

**`PersonalAIUserID` = the EvenAI account id** (`User.id.uuidString`) — the
value already flowing through `ownerBox.ownerID` today. **No change to
`RootView.swift`, no change to how `ownerID` is sourced.**

The CloudKit adapter maintains a **private infrastructure binding**, stored
in adapter-local state (not in any record, not in any bundle):

```
CloudKitAccountBinding {
    personalAIUserID:  String   // canonical, portable
    ckUserRecordName:  String   // CKContainer.userRecordID().recordName — infra only
    boundAt:           Date
}
```

- On first successful CloudKit use for a given `PersonalAIUserID`, the
  adapter records the binding.
- Before every sync it checks: does the current
  `CKContainer.userRecordID().recordName` still equal `ckUserRecordName` for
  the active `personalAIUserID`? If not → **account-switch safe state** (see
  next section).
- `PersonalAIUserID` is what gets written to `ownerID`, used for
  `stableID`, and used for R2 keys. CloudKit identity stays entirely inside
  the adapter.
- Migration to another provider: the new adapter creates its own binding
  (`personalAIUserID ↔ postgresUserRow`, etc.). No record touched, no
  bundle touched, no `stableID` change.

If Sign in with Apple is later added (decision-doc option), the SIWA `sub`
also becomes an **infra identity** mapped to `PersonalAIUserID` — never the
canonical id itself.

### RISKS

| Risk | Mitigation |
|---|---|
| The EvenAI account id itself is backend-ish (issued by the Railway auth service) | Per `User.swift` it is stable across the anonymous→claimed transition and is the app's own account concept, not a session token. If EvenAI's auth backend ever changes, `PersonalAIUserID` can be pinned to a locally-generated UUID persisted in the bundle — an additive change, decided then, not now. |
| Two EvenAI accounts on one physical device sharing one iCloud account | The binding is keyed by `personalAIUserID`; the adapter refuses to sync records whose `ownerID` ≠ the active `personalAIUserID`. Zone data is not shared between EvenAI accounts without an explicit user action. |
| `ownerID == nil` legacy local records (created before auth) | On first authenticated sync, `pendingChanges()` already stamps `record.ownerID ?? owner`. Acceptable — they adopt the current `PersonalAIUserID`. |

## ICLOUD ACCOUNT SWITCH SAFETY

**Scenario:** user on Apple ID **A** syncs Personal AI → signs out of iCloud
→ signs into Apple ID **B**.

### Requirements (all enforced)
- B must never inherit A's cloud identity or A's data.
- A's local Personal AI data must not silently upload into B's cloud.
- The switch must be **detected**.
- Local data is **never deleted automatically**.
- The app enters an explicit **reconciliation** state.
- The user is **informed before** any migration/merge.
- **No automatic cross-account merge, ever.**

### Mechanism

1. **Observe** `Notification.Name.CKAccountChanged`. On fire, and on every
   app foreground, and before every `sync()`:
   fetch `CKContainer.accountStatus()` and (if `.available`)
   `CKContainer.userRecordID()`.
2. **Compare** the current `ckUserRecordName` to the stored
   `CloudKitAccountBinding.ckUserRecordName` for the active
   `PersonalAIUserID`.
3. **Cases:**

   | Situation | Adapter behaviour |
   |---|---|
   | `accountStatus == .noAccount` (signed out) | Sync frozen. `PersonalCloudEnvironment` effectively degrades to "paused — iCloud signed out". **All local data retained.** No uploads, no deletes. |
   | Signed into the **same** account (`ckUserRecordName` matches) | Normal sync. |
   | Signed into a **different** account (`ckUserRecordName` differs from the binding) | **`accountMismatch` safe state.** `cloudSyncEnabled` is forced to a non-syncing state for this `PersonalAIUserID`. **Nothing is pushed. Nothing is pulled. Nothing local is deleted.** The UI shows: *"You're signed into a different iCloud account than the one your Personal AI was syncing with. Your data on this device is safe and untouched. Choose what to do."* Options offered to the user (no default action): (a) keep using local-only, (b) start syncing **this device's** data to the new iCloud account as a **fresh** cloud dataset (explicit, creates a new binding), (c) if the new iCloud account already has Personal AI data for this `PersonalAIUserID`, offer an explicit restore/merge — still user-initiated. |
   | Binding exists for `PersonalAIUserID` but the new iCloud account has **no** `PersonalAICore` / `PersonalAIChat` zones | Same `accountMismatch` state; option (b) is the natural choice; still explicit. |
   | No binding yet (first ever CloudKit use) | Create the binding for the current account; proceed. |

4. **`PersonalAIUserID` unchanged** across the switch (the EvenAI account is
   the same). Only the *infra* binding is in question. This is exactly why
   the canonical id must not be the CloudKit id — otherwise an iCloud switch
   would look like a *user* switch.

5. **Re-entry:** if the user signs back into account A, the original binding
   matches again and sync resumes normally — no data was lost because
   nothing was deleted or cross-written.

### Tests (added to the plan)
- `accountSwitch_detectedOnCKAccountChanged` — binding mismatch flips to
  `accountMismatch`, `sync()` returns `.skipped`/frozen.
- `accountSwitch_neverAutoUploads` — with pending local changes and a
  different iCloud account, `push` is never called.
- `accountSwitch_neverAutoDeletesLocal` — local memory/message stores are
  byte-identical before and after the switch.
- `accountSwitch_noAutoMerge` — the new account's existing zone data is not
  pulled into local until the user explicitly chooses restore.
- `accountSwitch_reentryResumes` — switching back to the original account
  matches the binding and resumes without duplication.
- `signOut_freezesSyncKeepsData` — `.noAccount` → frozen, full local
  retention.
- `stableIDUnchangedAcrossICloudSwitch` — `SyncableStyleProfile.stableID`
  and every `ownerID` are unchanged because `PersonalAIUserID` is unchanged.

## CUSTOM ZONE DESIGN

### FINAL DEVELOPMENT SCHEMA — ZONE DECISION: **B (two custom zones)**

Not one zone (A), not three or more. Exactly two, with fixed stable names:

| Stable zone name | Record types | Profile |
|---|---|---|
| **`PersonalAICore`** | `Memory` (memories + projects + people + episodes + knowledge, all by `MemoryCategory`), `Rule`, `StyleProfile` | small, bounded, high-value; must restore **first** and stay cheap forever |
| **`PersonalAIChat`** | `Conversation`, `Message` | append-heavy, unbounded, grows for years; restores **second**, in the background |

Both are `CKRecordZone.ID(zoneName: <name>, ownerName: CKCurrentUserDefaultName)`
in `container.privateCloudDatabase`. The names are permanent (a rename after
Production deploy is a data migration).

**`Revision` is deliberately NOT a CloudKit record type in v1.** In the
current architecture revisions do not round-trip through the cloud at all —
`snapshot()` returns a `PersonalDataBundle` and revision history stays local
(and in local backup/export). If cross-device revision history is later
built, a `Revision` record type is added at that time — **CloudKit permits
adding record types and zones to a Production schema** (only *removing* or
*retyping* fields is blocked), so deferring it carries no penalty. It would
land either in `PersonalAICore` or, if revision volume proves high, a third
zone `PersonalAIHistory` — decided then, before that feature ships.

So the **v1 Development schema is 5 record types across 2 zones.**

### Why the second zone is *required*, not organizational convenience

Three concrete properties, each of which one combined zone cannot provide,
and the layout is expensive to change after a Production deploy:

1. **Change-token-expiry re-fetch cost.** CloudKit `CKServerChangeToken`s
   expire (long offline periods, server-side maintenance/compaction, and
   after any restore-from-snapshot). On expiry the adapter must re-fetch
   that zone from a `nil` token. With **one** combined zone, every expiry =
   re-download of the **entire multi-year message history** just to
   reconcile a handful of memory edits. With the split, a core-token expiry
   re-fetches only the small `PersonalAICore` set; the `PersonalAIChat`
   re-fetch is independent and can be backgrounded / deferred.
2. **Restore prioritization.** On a fresh device, records arrive in
   server-change order — with one zone, memory records are interleaved
   throughout the message stream and the restore is only "done" when
   everything has downloaded. With two zones, `PersonalAICore` is fetched
   and applied first (seconds) → Personal AI is fully functional via
   `PersonalAIContextBuilder` → `PersonalAIChat` streams in afterwards,
   resumable from its per-page token.
3. **Failure isolation.** A poison record or a pathological page in the
   high-churn chat zone cannot stall memory sync.

### Why not three or more zones
- Custom zones have no per-zone record-count cap that matters at personal
  scale; the real limit is the **user's iCloud quota**.
- Per-category / per-conversation zones would multiply token bookkeeping and
  cross-zone reconciliation for no benefit — memories are used on-device as
  one set, and messages are already independently syncable records.
- A third zone is justified only if/when incremental revision sync is built
  *and* revision volume is shown to be large — an additive decision at that
  point.

### Implications of the two-zone decision

| Aspect | Implication |
|---|---|
| **CKSyncEngine** | Not used on the data path (see CKSYNCENGINE DECISION). Were it ever adopted, one `CKSyncEngine` instance can manage multiple zones, or one engine per zone — two zones does not preclude it. |
| **Change tokens** | One `CKServerChangeToken` per zone. `SyncPullResult.cursor` = base64 of `{"core":"<token|null>","chat":"<token|null>"}`, opaque to `PersonalAISyncEngine`. A garbage/partial/expired cursor is **safe** — `changeTokenExpired` is handled per zone and triggers a full re-fetch of *that zone only*. |
| **Atomic writes** | `CKModifyRecordsOperation` atomicity is **per-zone anyway** — CloudKit has no cross-zone atomic write. We never need one: memories and messages are independent. Each push chunk is single-zone, `isAtomic = true`, ≤200 records. |
| **Fresh-device restore** | `PersonalAICore` fetched + applied first → usable in seconds. `PersonalAIChat` second, paged, resumable, backgroundable. This is the primary motivation. |
| **Account switching** | The `CloudKitAccountBinding` check is **container-level**, not zone-level — unaffected by zone count. `accountMismatch` freezes sync for both zones equally; no zone is uploaded/pulled/merged. |
| **Zone deletion** | "Delete Personal AI Account" / `deleteAllData` deletes **both** zones. One `CKModifyRecordZonesOperation` accepts multiple `recordZoneIDsToDelete`, so it is still **one operation**. Clears the local side-table, both tokens, and the account binding. |
| **Backup** | `snapshot()` fetches both zones and assembles **one** `PersonalDataBundle`. Zones are a CloudKit-only concept — they appear nowhere in the bundle, the R2 backup, or the export archive. Backup/export formats are unchanged. |
| **Long-term message volume** | Isolated in `PersonalAIChat`. `PersonalAICore` operations (the ones on the interactive path) stay cheap forever regardless of chat size. Message pagination/archival (the separate workstream) operates entirely within `PersonalAIChat` and never touches core. |
| **Provider-independent domain model** | Zones are a CloudKit concept and appear in **zero** domain types, wire types, `PersonalDataBundle`, or the export format. A Postgres/Supabase adapter ignores the concept entirely. No leakage. |

### Simplest safe architecture
One zone is *simpler* but not *safe* at long-term scale (the change-token-
expiry full-rescan of years of messages). Two zones is the **smallest
arrangement that is safe**. Three or more is unjustified today. → **two.**

### Not created in STEP 1

### Not created in STEP 1
Zone creation is runtime-safe and happens in STEP 2/3 against **Development**
only, on a sandbox iCloud account: two `CKModifyRecordZonesOperation`s add
two empty zones; no user data; fully reversible by deleting the zones.

## RECORD TYPE MAPPING

### CURRENT ONE-BLOB DESIGN: **NO**

The design is — and was — **one `CKRecord` per canonical entity**, keyed by
that entity's stable UUID. There is **no** record that holds more than one
entity, and **no** "whole Personal AI state" record. The comparison the
review asked for:

| Option | What it would look like | Verdict |
|---|---|---|
| **A. one encoded state record** | `PersonalAIState` · `recordName = "state-<userid>"` · `payload = <entire memory DB + all rules + all conversations + all messages as one blob>` | **Rejected.** One corrupt/oversized write loses everything; every message append rewrites the whole blob; no incremental sync; no partial restore; 1 MB CloudKit record limit blown immediately; useless for Postgres migration. |
| **B. record-per-canonical-entity** (chosen) | `Memory` · `recordName = <memory UUID>` · fields: `payload` (that one memory's JSON, encrypted) + `recordKind`, `deletedAt`, `clientUpdatedAt`, `schemaVersion` | **Chosen.** Blast radius = one entity. Incremental. Partial restore. Well under size limits. 1:1 to Postgres rows. |

### The `payload` field — what it is and is not

Within each per-entity record, the entity's own canonical `Codable` JSON
(exactly what `PersonalSyncCodec` already produces for export/backup) is
stored in **one encrypted field, `payload`**, rather than exploded into a
wide set of typed CloudKit columns.

- This is **not** a blob of multiple entities. It is one entity's ~1–4 KB of
  its own data.
- Why a single field rather than typed columns:
  1. **`CKRecord` stays a pure adapter representation** — it never becomes
     the canonical model. The mapper is trivial and lossless.
  2. **Byte-identical to the export/backup format** — one serialization,
     one set of round-trip tests.
  3. **Conflict resolution needs the whole prior state anyway** —
     `SyncConflict.serverPayloadJSON` is a direct field read.
  4. **Minimal production schema surface** — fewer fields that could later
     need removing (CloudKit blocks field removal in Production).
- Blast radius of a corrupt `payload`: **one entity**. The plaintext
  metadata fields (`recordKind`, `deletedAt`, `clientUpdatedAt`) plus any
  the on-device revision history usually allow that one entity to be
  reconstructed or at least identified. It **cannot** damage any other
  record.
- **Content stays encrypted:** `payload` and `deletedAt` go in
  `CKRecord.encryptedValues`. `recordKind` / `clientUpdatedAt` /
  `schemaVersion` are plaintext (no memory content — kind labels and
  timestamps only) so the Console is debuggable and future non-content
  sorting is possible.

### Common fields (every record type)

| Field | CK type | Encrypted? | Purpose |
|---|---|---|---|
| `payload` | `Bytes` | **yes** | This entity's canonical `Codable` JSON. |
| `recordKind` | `String` | no | `"memory"` … — defensive routing / Console. |
| `deletedAt` | `Date/Time` | **yes** | Soft tombstone; mirrors payload. |
| `clientUpdatedAt` | `Date/Time` | no | Entity `updatedAt`; stable sort/debug key. |
| `schemaVersion` | `Int64` | no | `PersonalMemoryDocument.currentSchemaVersion` at write. |

CloudKit's built-in `recordChangeTag` / `creationDate` / `modificationDate`
provide server-side versioning — no "revision" column is added to CloudKit;
the domain `revision` lives inside `payload`.

### Per-type

| RECORD TYPE | ZONE | RECORD ID | one/many entities | payload contents | queryable fields | references | deletion / tombstone | version field | last-modified |
|---|---|---|---|---|---|---|---|---|---|
| **Memory** (memories, **projects**, **people**, **episodes**, knowledge — all `MemoryRecord`, distinguished by `MemoryCategory`; **no separate CK type per category**) | `PersonalAICore` | `recordName = memory.id.uuidString` | **one** canonical entity | one `MemoryRecord` JSON (category, scope, `canonicalContent`, `structured`, `entities`, provenance UUID arrays, `supersedesID`/`supersededByID`, confidence, importance, `embeddingModelVersion`, …) | `recordKind`, `deletedAt`, `clientUpdatedAt` (metadata only) | provenance + supersede links are **UUIDs inside payload**, not `CKReference` (keeps referential rules in `MemoryMerger`, avoids CloudKit cascade semantics) | soft: `deletedAt` field + payload; hard-delete callback → local soft tombstone; never resurrected (engine guard) | `payload.revision` + `recordChangeTag` | `clientUpdatedAt` |
| **Rule** | `PersonalAICore` | `recordName = rule.id.uuidString` | one | one `Rule` JSON | same | none | soft tombstone; `ConflictPolicy.ruleUnion` | `payload.revision` + tag | `clientUpdatedAt` |
| **StyleProfile** (per-user singleton) | `PersonalAICore` | `recordName = SyncableStyleProfile.stableID(personalAIUserID).uuidString` (deterministic — always collides with itself) | one | one `PersonalAIStyleProfile` JSON | `recordKind`, `clientUpdatedAt` | none | never tombstoned; `ConflictPolicy.newestWins` | `PersonalSyncState.styleRevision` + tag | `clientUpdatedAt` |

| **Conversation** | `PersonalAIChat` | `recordName = conversation.id.uuidString` | one | one `PersonalAIConversation` JSON (`title`, `doNotRemember`, `messageCount`, …) | `recordKind`, `deletedAt`, `clientUpdatedAt` | messages link via `conversationID` UUID **in their own payload** | soft tombstone; a `doNotRemember` conversation is **never written to CloudKit** (filtered in `pendingChanges()`) | `payload.revision` + tag | `clientUpdatedAt` |
| **Message** | `PersonalAIChat` | `recordName = message.id.uuidString` | one | one `PersonalAIChatMessage` JSON (`conversationID`, `role`, `text`, `timestamp`, `eligibleForMemory`) | `recordKind`, `deletedAt`, `clientUpdatedAt` | `conversationID` UUID in payload | append-only; `deletedAt` supported but rare; `ConflictPolicy.appendOnly` (never overwrite text) | `payload.revision` + tag | `clientUpdatedAt` (starts == `timestamp`) |

**Explicitly:**
- **Episodes / projects / people** → `Memory` records with the matching
  `MemoryCategory`. No separate type, zone, or sync path.
- **Sources / provenance** → UUID arrays inside the `Memory` payload. Not CK
  records, not `CKReference`s.
- **Tombstones** → the `deletedAt` field/payload on the entity's own small
  record + CloudKit's delete-change callback. No separate tombstone record.
  See TOMBSTONE DESIGN.
- **Revisions** → **local only in v1** — not a CloudKit record type.
  Future direction: separate immutable `Revision` records. See REVISION
  DESIGN.
- **Sync metadata / change tokens / the `PersonalAIUserID ↔ CKUserRecordName`
  binding** → **local only**, never a CloudKit record. Rebuildable from a
  `nil`-token fetch.

### STABLE RECORD ID DESIGN

**For every type, `CKRecord.ID(recordName: <canonical UUID>.uuidString,
zoneID: <core|chat>)`.** The adapter **always constructs the ID** before a
save. CloudKit **never** generates an identity the system depends on.

| Entity | recordName source | Zone |
|---|---|---|
| memory / project / person / episode | `MemoryRecord.id` | `PersonalAICore` |
| rule | `Rule.id` | `PersonalAICore` |
| style profile | `SyncableStyleProfile.stableID(personalAIUserID)` (deterministic) | `PersonalAICore` |
| conversation | `PersonalAIConversation.id` | `PersonalAIChat` |
| message | `PersonalAIChatMessage.id` | `PersonalAIChat` |
| revision | *not a CloudKit record in v1* — `RecordRevision.id` if ever synced | (future) `PersonalAICore` / `PersonalAIHistory` |
| tombstone | *not a record* — `deletedAt` on the entity above | — |

`remoteID` (currently unused `String?`) is set to the zone-qualified name
(`"PersonalAICore:<uuid>"`) as a debug hint only; nothing keys off it.
Re-restore preserves `client_id`s (existing importer) so it never
duplicates. A Postgres migration reuses the same UUIDs as primary keys.

## REVISION DESIGN

**Never an embedded array/blob inside an entity record.** Editing a memory
rewrites only that memory's small record — its history is not carried in it.

### v1: revisions are local, not a CloudKit concept
This matches the architecture as built today: `RecordRevision`s live in the
local store and travel in local backup/export bundles. `snapshot()` returns
a `PersonalDataBundle`; revision history is reconstructed on the device that
holds it. **No `Revision` CloudKit record type exists in the v1 Development
schema. Nothing writes one.**

Consequence: a second device sees another device's *edit* (the new current
state) as soon as it syncs, and builds its own local history from that
point; the *pre-edit* history entry is not transferred. On-device
undo/restore and export always have complete local history on the device
where the edits happened. Acceptable for an audit/undo feature.

### Future direction if cross-device revision history is built — **option A (separate immutable records)**
- Each `RecordRevision` (pure value type: `revisionID`, `recordID`,
  `recordKind`, `version`, `changedAt`, `source`, `reason`,
  `previousPayloadJSON`) → one immutable `Revision` `CKRecord` keyed by
  `revisionID`, in `PersonalAICore` (or a new `PersonalAIHistory` zone if
  volume proves high).
- **Never updated** — written once, no conflict possible. Editing a memory
  then writes the small `Memory` record **plus** one small `Revision`
  record; nothing large is rewritten.
- **Retention** (unchanged from Phase 2): `userConfirmed` → full history;
  inferred → last ~10. Pruned `Revision` records are **hard-deleted**
  (bounded derived audit data; a tombstone adds no value).
- **Cost of building it:** two tiny additive Core additions
  (`PersonalRecordKind.revision`; `PersonalSyncState.syncedRevisionIDs:
  Set<String>`), consistent with the locked "extend Phase 1/2 types
  additively" decision. **Not** part of STEP 1.
- **No penalty for deferring:** CloudKit permits adding record types (and
  zones) to a Production schema later; only field removal/retyping is
  blocked.

## TOMBSTONE DESIGN

- **Representation:** the entity keeps its own `CKRecord`; `deletedAt` is
  set (encrypted field + inside `payload`); `payload` content may be trimmed
  to the minimum needed for the merger's resurrection guard
  (id, kind, `deletedAt`, `updatedAt`, `revision`).
- **Propagation:** on pull, both an explicit `deletedAt` and CloudKit's
  `recordWithIDWasDeletedBlock` are converted to a local soft tombstone.
- **Resurrection guard (existing):** an incoming `deletedAt` wins even over a
  lower-revision local non-deleted copy. A stale re-add never revives a
  deleted record.
- **Retention:** tombstones for memory / rule / conversation are kept
  **indefinitely** (they are tiny and the guard needs them for devices that
  sync infrequently). Message tombstones likewise. A far-future optional
  prune of tombstones older than N years *that are confirmed synced
  everywhere* is possible but **not** in scope.
- **Hard delete** happens only via **zone deletion** ("Delete Personal AI
  Account" / `deleteAllData`), which removes both zones in full.

## LARGE CHAT HISTORY DESIGN

Personal AI chat history is expected to grow for years. The schema must
**never require rewriting a conversation or the Personal AI state to append
one message.**

**It does not:** one message = one independent `Message` record in
`PersonalAIChat`. Appending message N+1 is a single small record save. The
parent `Conversation` record is updated only for cheap metadata
(`messageCount`, `lastMessageAt`) — and that update is itself a tiny record,
not a rewrite of the messages.

| Scale | Approx size (msgs @ ~0.3–1 KB payload) | Incremental sync | Fresh-device restore | Notes |
|---|---|---|---|---|
| **10,000** | ~5–20 MB | trivial — only changed records move | `PersonalAICore` restores in seconds; `PersonalAIChat` in well under a minute | comfortable |
| **100,000** | ~50–200 MB | trivial | **`PersonalAICore` usable in seconds**; `PersonalAIChat` pages in over `CKFetchRecordZoneChangesOperation`'s automatic pagination (`moreComing`), persisting the per-page token so restore is **resumable** if interrupted; UI shows chat history "still loading" without blocking memory features | the two-zone split is what makes this acceptable |
| **1,000,000** | ~0.3–1 GB | still record-level, but total volume is large for CloudKit **and for the user's iCloud quota** | zone-change paging works, but a full cold restore of 1M records is minutes-to-longer on cellular | **Beyond the current *local* architecture regardless of CloudKit:** `LocalPersonalDataStore.exportBundle` / `conversations.allMessages()` load all messages into memory. A **message pagination + archival policy** (old messages → cold export, dropped from the hot sync set) is a **separate required workstream**. The record-per-message schema is the correct foundation for it and does not need to change. |

**Pagination & incremental restore:**
- Pull is one `CKFetchRecordZoneChangesOperation` over both zones; CloudKit
  returns changes in pages with `moreComing`; the adapter persists each
  zone's token per page → **resumable**.
- Restore order: `PersonalAICore` fully, then `PersonalAIChat` newest-first
  by conversation (so recent chats appear first).
- A future "load older messages" UI reads from the local store lazily per
  conversation; the sync layer already only moves deltas.

## CKSYNCENGINE DECISION

**Unchanged: do NOT use `CKSyncEngine` on the data path.** Implement the
adapter with `CKModifyRecordsOperation` + `CKFetchRecordZoneChangesOperation`
+ per-zone `CKServerChangeToken`, behind the existing `PersonalCloudService`.

Reasons (fit with the request/response seam; provider independence; reuse of
the existing engine's retry / idempotency / conflict-loop / pagination /
cancellation; API maturity) are in the prior revision and stand. Cost: we
implement batching, backoff, and account-change handling ourselves — small,
and mostly already present.

### Impedance points — solved in the adapter, NOT the domain model

1. **Cursor** — `SyncPullResult.cursor` = base64 JSON of the two per-zone
   tokens. Opaque to the engine.
2. **`baseRevision: Int` vs `recordChangeTag: String`** — the adapter keeps
   a persisted local side-table `recordName → (changeTag, syntheticRevision)`,
   assigns a monotonic `syntheticRevision` per record as it observes new
   server versions, returns it as `SyncRecordEnvelope.serverRevision`. No
   change to `SyncRecordEnvelope` / `PersonalSyncState` / any Core type.
3. **Conflict → `SyncConflict`** — on `CKError.serverRecordChanged`,
   `error.serverRecord.payload` → `serverPayloadJSON`; `serverRevision` =
   the side-table synthetic; hand to the existing
   `PersonalConflictResolver`.
4. **Idempotency** — CloudKit saves are idempotent on `recordName` + change
   tag; the adapter keeps a small in-memory `idempotencyKey → result` cache
   only for the "timeout, unknown outcome, immediate retry" window.
5. **Post-restore cursor** —
   `PersonalAICloudRestoreCoordinator.syncCursor(to:)` currently sets
   `cursor = String(maxRevision)` (a mock-ism). For CloudKit the correct
   cursor after a snapshot is the pair of zone tokens the snapshot fetch
   ended on. **Small additive infra change** (see FILES TO CHANGE). A wrong
   value is still *safe* (per-zone `changeTokenExpired` → full re-fetch of
   that zone), so this is a correctness/efficiency fix, not a data-safety
   fix.

### Change-token / side-table / account-binding: local, not in-cloud (v1)
All adapter bookkeeping is persisted **locally** (a small sealed file beside
the encrypted cache). It is per-device plumbing and fully rebuildable — drop
it and the next sync refetches from `nil` tokens and re-hydrates.

## SYNC FLOW

`CloudKitPersonalCloudService` conforms to the **existing**
`PersonalCloudService`. `PersonalAISyncEngine.sync()` is unchanged.

### push(_ request:) -> SyncPushResult
1. `accountStatus()` → not `.available` ⇒ throw `.unauthorized`
   (engine → `.failedRetryable`, nothing lost).
2. **Account-binding check** (see ICLOUD ACCOUNT SWITCH SAFETY) → mismatch ⇒
   throw a distinct non-retryable `"account-mismatch"` code; **nothing
   pushed**.
3. Ensure both zones exist (create-if-missing, cached).
4. Per envelope → build a `CKRecord` of the mapped type in the mapped zone,
   `recordName = envelope.id.uuidString`, `encryptedValues["payload"]`,
   `deletedAt`, `recordKind`, `clientUpdatedAt`, `schemaVersion`. Updates
   start from the side-table's stored record (correct change tag); new
   records are fresh; tombstones are a save with `deletedAt` set.
5. Chunk ≤200 records per `CKModifyRecordsOperation`,
   `savePolicy = .ifServerRecordUnchanged`, `isAtomic = true` per chunk,
   routed by zone.
6. Success → update side-table; emit accepted envelopes with `remoteID` +
   `serverRevision`.
7. `serverRecordChanged` → `SyncConflict`. `limitExceeded` → split + retry.
   `requestRateLimited` / `zoneBusy` / `serviceUnavailable` / network →
   retryable code; committed chunks already returned, remainder stays
   pending. `quotaExceeded` → `"quota"` code, nothing dropped.

### pull(ownerID:since:) -> SyncPullResult
1. `accountStatus()` + account-binding gate.
2. Decode cursor → two `CKServerChangeToken?`.
3. One `CKFetchRecordZoneChangesOperation` over `[PersonalAICore,
   PersonalAIChat]` with per-zone `previousServerChangeToken`.
4. `recordWasChangedBlock` → envelope (`serverRevision` = side-table
   synthetic); update side-table.
5. `recordWithIDWasDeletedBlock` → envelope with `deletedAt = now`, empty
   payload → local tombstone.
6. Capture new per-zone tokens; persist locally; `cursor` = base64 of both;
   `hasMore` = any zone `moreComing`.
7. `changeTokenExpired` for a zone → discard that zone's token, re-fetch it
   from `nil` transparently.
8. Zone-not-found → treat as empty; created on next push.

### snapshot(ownerID:) -> PersonalDataBundle
Full fetch of both zones from `nil` tokens, paging until done →
`PersonalBundleAssembler.assemble`. Returns/persists the ending token pair
so the post-restore cursor is correct.

### deleteAllData(ownerID:)
Delete both zones (`CKModifyRecordZonesOperation`); clear the local
side-table, tokens, and account binding.

### Triggers (unchanged): `open()`, foreground, after a Personal AI turn's
async extraction. No push subscription in v1.

## ERROR HANDLING

Engine invariant unchanged: **a sync failure never deletes or corrupts valid
local data; a failed push keeps every change queued; a failed pull leaves
the cursor untouched.**

| Condition | Signal | Adapter | Engine | Local data |
|---|---|---|---|---|
| iCloud signed out | `accountStatus == .noAccount` | throw `.unauthorized` pre-op | `.skipped`/`.failedRetryable` | **fully retained**, frozen, UI: "iCloud signed out" |
| **Different iCloud account** | binding mismatch | throw `"account-mismatch"`, no push/pull | `.failedRetryable`/frozen | **fully retained**, `accountMismatch` UI, no auto anything |
| Restricted / undetermined | `.restricted` / `.couldNotDetermine` | retryable | `.failedRetryable` | retained |
| Network down | `.networkUnavailable` / `.networkFailure` | `.offline` | `.failedRetryable` | retained, queued |
| Rate limited / zone busy / service down | `.requestRateLimited` / `.zoneBusy` / `.serviceUnavailable` | honour `retryAfterSeconds` | `.failedRetryable` | retained |
| iCloud full | `.quotaExceeded` | code `"quota"`, **drop nothing** | `.failedRetryable(code:"quota")` | **fully retained**, UI: "iCloud storage full — sync paused" |
| Stale write | `.serverRecordChanged` | → `SyncConflict` → resolver per `ConflictPolicy` | resolved deterministically, re-pushed | authoritative local data preserved; loser kept as a `RecordRevision` |
| Token expired | `.changeTokenExpired` | transparent per-zone full re-fetch | success | idempotent, id-keyed upserts, no dupes |
| Batch too large | `.limitExceeded` | split + retry | success | — |
| Partial failure | `CKError.partialFailure` | per-record: accepted / conflict / retryable; committed chunks returned | mixed; remainder stays pending | consistent |
| Undecodable server payload | our decode guard | abandon pull, **cursor not advanced**, `"decode"` | `.failedRetryable(code:"decode")` | untouched (existing guard) |
| Cancellation | `Task.isCancelled` | ops cancelled | `.skipped(.cancelled)` | consistent, pending stays pending |

Diagnostics: ids, counts, `hash(personalAIUserID)`, `CKError.Code` numbers
only — never payload content.

## SECURITY MODEL

Path: `CKContainer("iCloud.com.evenai.app").privateCloudDatabase` → zones
`PersonalAICore` / `PersonalAIChat` → records with `payload` + `deletedAt`
in `encryptedValues`.

| Question | Answer (not overclaimed) |
|---|---|
| Who can read/write? | Only the signed-in iCloud account, on that account's own Apple devices. No sharing, no public surface, no cross-user path. |
| Encryption | In transit: Apple TLS. At rest: Apple-managed for the record; **additionally** `payload` + `deletedAt` use `encryptedValues` (keys tied to the user's account/devices, **not** readable by Apple server-side or in the Console). Plaintext fields carry only kind labels, timestamps, schema version. Local cache stays AES-GCM-sealed (Phase 2), independent of CloudKit. |
| Sign out of iCloud | `.CKAccountChanged` → `.noAccount` → sync frozen, **all local data kept**. Records already in CloudKit stay in the user's account. |
| Different Apple ID signed in | `accountMismatch` safe state — **no auto upload, no auto delete, no auto merge**, user informed. |
| iPhone lost | Data is in the user's iCloud account. Lost device holds only an encrypted cache with a device-local Keychain key. |
| New iPhone, same Apple ID | `snapshot()` → `.replaceAll` import → full restore. |
| Developer browsing private records in the Console? | **Production: no** (Apple blocks developer access to other users' private data). **Development: the developer sees their *own* sandbox account's data** — and `encryptedValues` fields still show as encrypted blobs. A real end user's memory is not visible to the developer. |
| Future server-side Personal AI | A headless backend **cannot** read this private DB without the user's interactive `ckWebAuthToken`. Known blocking limitation for Phase 3. |

## NEW IPHONE RESTORE FLOW

1. User signs the new iPhone into their Apple ID, installs EvenAI.
2. `PersonalAIService.open()` runs; container is `.connected` with
   `CloudKitPersonalCloudService`.
3. Adapter: `accountStatus() == .available`; `PersonalAIUserID` = the EvenAI
   account id; adapter creates a fresh `CloudKitAccountBinding` (no prior
   binding on a new device).
4. Local store empty → `needsCloudRestore` set → `restoreFromCloud()`.
5. `snapshot(ownerID:)` → **`PersonalAICore` fully first** (Personal AI
   immediately usable) → **`PersonalAIChat` paged in, resumable** →
   `PersonalBundleAssembler.assemble` → `PersonalDataImporter.validate` →
   `importBundle(.replaceAll)`.
6. Cursor set to the snapshot's ending **token pair** (the small infra fix).
7. `needsCloudRestore = false`; subsequent syncs incremental.
8. Snapshot unavailable/invalid → local left exactly as it was; fallback is
   the Cloudflare R2 backup (later) or a user-saved export archive.

**Duplicate-restore safety:** `client_id`s preserved; importer dedupes by
id; tombstones honoured; second run is a no-op.

## SERVER-SIDE AI LIMITATION

Unchanged and unresolved by STEP 1 — must be proven before Phase 3.
CloudKit's private DB has no server-to-server access to private data and no
server-side query/compute; a headless backend needs the user's interactive
`ckWebAuthToken`. Near-term server-side Personal AI must be **client-mediated**
(phone builds context, POSTs to a stateless endpoint). If that proves
insufficient, canonical storage migrates to Postgres **without changing the
domain model or the export format** — the `PersonalCloudService` seam +
stable UUIDs + the provider-independent `PersonalAIUserID` make it an
adapter swap. This plan adds one adapter and one entitlements file and
touches **no Core type**, so it does nothing to impede that migration.

## PRODUCTION-SCHEMA SAFETY

CloudKit **Development** and **Production** are separate schemas +
datastores. All STEP 1 implementation is **Development only**.

Migration process (each gate = a human review point):
1. **Development schema creation** — the **5 v1 record types** (`Memory`,
   `Rule`, `StyleProfile`, `Conversation`, `Message`) across the **two

   **account switch A→B→A**; airplane-mode reconcile. **Only step that

6. **Only after review: Deploy schema to Production.** After promotion:
   fields and types can be **added**, but **not removed / retyped**; index
   changes constrained. The minimal field set is deliberately small so
   there is very little that could ever need removing.

## TEST PLAN

Deterministic tests keep using the mock; CloudKit-specific tests are
additive.

### A. Mapping / codec (offline, no account, no network)
- each of the **5 v1 types** — `MemoryRecord`, `Rule`,
  `PersonalAIConversation`, `PersonalAIChatMessage`, `SyncableStyleProfile`
  → `CKRecord` → back — **byte-identical payload**, all fields preserved
- **stable IDs** — `recordName == entity.id.uuidString` out and back; correct
  zone per type (`Memory`/`Rule`/`StyleProfile` → `PersonalAICore`;
  `Conversation`/`Message` → `PersonalAIChat`)
- **`payload.revision` survives** the round trip
- **`RecordRevision` never reaches the mapper** — assert it is excluded from
  `pendingChanges()` output and is not a mapped kind (revisions are
  local-only in v1)
- **unknown future field tolerated** — extra `CKRecord` key and extra
  payload-JSON key both still decode and are preserved on re-encode
- `payload` + `deletedAt` actually land in `encryptedValues`, not the
  plaintext dictionary

### B. Adapter contract (fake `CKDatabase` / `CKError` fixtures)
- **duplicate cloud delivery idempotent** — same changed record twice → one
  upsert
- **conflict resolution deterministic** — `serverRecordChanged` →
  `SyncConflict` → resolver; same inputs → same output regardless of device
  order; per `ConflictPolicy` per kind
- **local newer vs cloud older** / **cloud newer vs local older** — correct
  winner, loser retained as a `RecordRevision`
- **cursor opaque** — garbage cursor → safe per-zone full re-fetch, no crash,
  no loss
- **partial batch** / **`limitExceeded`** — correct accept/conflict split;
  chunk split succeeds

### C. Data-safety invariants
- **CloudKit unavailable keeps local data** — `.networkFailure` /
  `.serviceUnavailable` → `.failedRetryable`, every pending change still
  pending, stores byte-identical
- **iCloud signed out keeps local data**
- **quota exceeded keeps local data** — distinct code, nothing dropped/
  overwritten
- **partial sync does not clear cache** — page 1 ok, page 2 fails → cursor
  not advanced past a safe point, no local deletions
- **cancelled sync safe**
- **malformed server payload** — undecodable `payload` JSON → pull abandoned,
  cursor unchanged, local untouched

### D. Restore / new install
- **fresh-install restore** — empty local + populated Development container →
  `snapshot()` → `.replaceAll` → memories, rules, projects, people,
  episodes, style, conversations, messages all present; restored memory
  usable by `PersonalAIContextBuilder`. (Revisions are local-only in v1 — a
  fresh device starts its revision history from the restored state.)
- **core-before-chat ordering** — `PersonalAICore` applied and usable before
  `PersonalAIChat` finishes
- **resumable chat restore** — interrupt mid-`PersonalAIChat` paging →
  resume from the persisted per-page token, no duplicates
- **duplicate restore does not duplicate**
- **deleted records do not resurrect**
- **post-restore cursor** — first incremental `pull` fetches only genuinely
  newer changes (uses the token pair, not a revision number)

### E. Identity / account switch
- `accountSwitch_detectedOnCKAccountChanged`
- `accountSwitch_neverAutoUploads`
- `accountSwitch_neverAutoDeletesLocal`
- `accountSwitch_noAutoMerge`
- `accountSwitch_reentryResumes`
- `signOut_freezesSyncKeepsData`
- `stableIDUnchangedAcrossICloudSwitch` — `PersonalAIUserID`, every

- `differentEvenAIAccountSameICloud_noCrossContamination`
- mock per-`ownerID` isolation tests continue to pass unchanged

### F. Large chat history (mock backend, generated volume)

## GO / NO-GO FOR STEP 1 IMPLEMENTATION

**Recommendation: GO** — implement `CloudKitPersonalCloudService` in the
CloudKit **Development** environment, after (a) Oleg reviews this revised
plan and (b) manual actions #1–#2 (Team ID) and #3–#4 (App ID iCloud
capability + container) are done.

Rationale:
- Storage is **record-per-canonical-entity**. A corrupt or oversized payload
  damages **one entity**, never the memory system.
- **Zero Core/Domain changes in v1.** `CKRecord` is a pure adapter
  representation; the canonical model and export format are untouched;
  `import CloudKit` is confined to three Infrastructure files.
- The canonical user identity (`PersonalAIUserID`) stays **app-level and
  provider-independent**. CloudKit's user id is infrastructure identity in
  an adapter binding. **`RootView.swift` is not changed.**
- **iCloud account switch** has an explicit safe design: detect, freeze,
  never auto-upload / auto-delete / auto-merge, inform the user.
- The data-safety invariant ("a sync failure never destroys authoritative
  local data") is preserved — the engine is untouched.
- Two zones keep memory restore fast regardless of years of chat history.
- Cost $0 (existing Apple Developer Program). No production schema, no
  production data, no external account, no Railway contact, no
  `AIConversationEngine` contact.

**NO-GO / stop conditions:**
- Team ID cannot be confirmed / membership inactive.
- The roadmap hardens on **autonomous server-side memory processing** in the
  near term → evaluate Postgres-as-PRIMARY first; CloudKit's server-access
  limitation would then be decisive.
- Review rejects the per-entity `payload`-field shape in favour of fully
  exploded typed CloudKit columns (possible, but enlarges the production
  schema surface and promotion risk — and would push `CKRecord` closer to
  being a second model).

**Still forbidden until separately approved:** deploying schema to
Production, creating the CloudKit container without review, configuring
Cloudflare / R2 / Workers, Sign in with Apple wiring, push-notification
capability, flipping `PersonalAIContainer.live` to `.connected` by default
(waits for the STEP 9 physical-device test, including the account-switch
matrix), starting G2 Phase 3.
